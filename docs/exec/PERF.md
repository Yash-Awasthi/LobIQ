# Build and runtime measurements

Machine and conditions: HW.md. Each entry: id, what, before -> after, command or file, commit.

## Build (2026-10-10)

- P1 Clean build, ccache off, 20 jobs: release 36.1 s -> 32.6 s; native (LTO) 25.6 s -> 23.7 s (d16c31c).
- P2 Cost is code generation more than parsing: pm_test.cpp alone 16.7 s full vs 4.2 s parse (-fsyntax-only); RapidCheck/gtest templates at -O3 dominate test files.
- P3 Header weight (preprocessed lines on their own): core/spsc.hpp 137k -> 29k (sched_yield and __builtin_ia32_pause instead of <thread> and <immintrin.h>); net/tape.hpp 110k -> 36k (GCC vector types and builtins instead of <immintrin.h>, realloc instead of <memory>); exec/oms.hpp 96k -> 34k (pm/rules.hpp split from pm/gamma.hpp, which pulled OpenSSL, sockets and the JSON reader); core/tsc.hpp: builtins and clock_gettime instead of <x86intrin.h> and <chrono>. apps/pm_live.cpp 224k -> 152k. Measure: build-free script, one header per translation unit, g++ -E | wc -l.
- P4 Heaviest standard headers measured: <chrono> 90k lines / 0.98 s, <filesystem> 80k, <thread> 77k, <fstream>/<sstream>/<iostream> ~70k each, <immintrin.h> 55k, <memory> 56k. Kept out of hot-path headers; still used in file I/O (pm/reader.hpp 104k, pm/session.hpp 142k) and apps.
- P5 Edit loop (touch a header, rebuild, ccache off): exec/oms.hpp 7.8 s; pm/msg.hpp 17.3 s -> 15.0 s after splitting pm_test.cpp (decoder tests to pm_decoder_test.cpp). Bound by the slowest dependent test file.
- P6 Tests at -O1 instead of -O3 (release preset): msg.hpp edit 15.0 -> 11.7 s, oms.hpp 7.8 -> 6.0 s, test run unchanged (2.9 s). Not adopted: release tests would no longer exercise -O3 code generation of header-only product code. Owner can choose.
- P7 Linkers: GCC LTO needs a GCC-plugin linker (bfd/gold); lld is installed but cannot do GCC LTO; mold not installed. Release links are small; native link of hft_tests ~10 s is LTO code generation, not linking.
- P8 Dead code removed: Philox AVX2 eight-lane path (no production caller; perf notes found it latency-bound and unused).

## Runtime (2026-10-10)

- R1 pm_live --replay (2.0M msgs, native, vCPUs 2,4): 1.92 s wall, RSS 35 MB, 8.4k minor faults (setup; ~1% of runtime). parse p50 538 ns, engine 177 ns.
- R2 SpscBytes first lap (8 MB ring, 600-byte records, consumer keeping up): p99 1.8 us, p99.9 3.4-6.4 us, max 71-164 us per write (page faults) -> Pool mapping (2 MB pages, pre-faulted): p99 104-136 ns, p99.9 223-244 ns, max mostly < 21 us (7f6a0ad). Affects live feed threads and the recorder ring, not replay.
- R3 C++26 (-std=c++26, GCC 15.2): decoder 517-525 ns/msg either standard (noise). libstdc++ 15 has no <inplace_vector> or <simd>; <experimental/simd> (TS) exists. No reason to switch now.
- R4 simdjson 3.13 On-Demand (haswell kernel) on the same 300k messages, same fields and the same price/size parsers: 430-443 ns/msg (1.41-1.45 GB/s) vs ours 504-516 ns/msg (1.21-1.24 GB/s); simdjson rejected 2 messages ours decodes. ~15% faster, but 7.6 MB of source (compile time on every includer), needs padded buffers, validates only what is read. Not adopted; if parse speed matters more, walk the tape's SIMD structural index in the single pass instead (its technique, not its code). Bench: ~/scratch/sj_bench.cpp.
- R5 Allocators (mimalloc, jemalloc): no effect possible on the trading path; steady state allocates nothing (alloc_test). Not tried.
- R6 Venue-mode engine per message (pm_exec replay, reference recording, arb on, pinned vCPU 2): p50 790 -> 556 ns, p99.9 16.7 -> 14.4 us; 470k -> 514k messages/s. Cause (perf cpu-clock, annotate): the arbitrage executor built a 64-byte leg view for every leg of every group on each book change (store-forwarding stalls); it now sums best prices from the books and builds views only when a window can be taken. Decision hash unchanged (3c8be7fa30920873). Remaining gap to the no-order path (189 ns) is the makers' order traffic.
- R7 Feed thread per WebSocket message (600-byte text frames in 16 kB reads, `hft_bench --benchmark_filter=Ws`, pinned vCPU 2): 84.7 -> 44.5 ns, 2 heap allocations -> 0. Before: TLS output to a stack buffer, appended to the parser, copied into a string per message, then into the ring. After: TLS decrypts into the parser's buffer (reserve/commit), each message is a view (unmasked in place), copied once into the ring; fragmented messages still join in a side buffer. Checks: alloc_test (zero in steady state), net tests, ws_fuzz (chunking never changes the messages), live paper run and recorder on the feed.
- R8 Receive time from the kernel (SO_TIMESTAMPNS through a recvmsg BIO under OpenSSL): a message's receive time is now when its bytes reached the kernel, not when the feed thread wrote it to the ring. New measurement, 60 s live paper run (25.6k messages): kernel stamp to ring p50 148 us, p99 410 us, p99.9 532 us, against ring to decision p50 96 us; so wire to decision is about 240 us p50, not the 96 us reported before. Most of it is the feed thread waking from poll(2) under WSL2: with the feed threads spinning it drops to 31 us p50 (R9); the rest (TLS decrypt, framing, the copy) was not split further. Recordings made from now on carry kernel times (replay is unaffected: it uses whatever times were recorded).
- R9 Feed threads spinning (`--spin-feeds`: poll(2) with a zero timeout and a pause, instead of sleeping up to 200 ms), live paper runs of 60 s, alternated to share market conditions (kernel stamp to ring, p50 / p99): sleeping 173 / 434 us and 175 / 409 us; spinning 31 / 174 us and 33 / 236 us (one spinning run had a 23 ms p99.9, likely the hypervisor descheduling a spinning thread). With the trading thread spinning too (`--spin --spin-feeds`): kernel to ring 31 / 209 us, ring to decision 8 / 69 us, so wire to decision about 39 us p50 against about 280 us with both sleeping. Cost: one busy core per connection plus one for the trading thread. Off by default on the laptop; the setting for a dedicated machine with isolated cores.

## Final check (2026-10-11)

- R10 Risk and order-manager micro-benchmarks (`hft_bench --benchmark_filter="Risk|Oms"`, pinned vCPU 2, back to back against the E6.1 commit 85f70d8 built the same way): risk check 19.4 -> 25.3 ns, order cycle 57 -> 78 ns. risk.hpp and the benchmark are unchanged; the disassembly shows link-time optimisation inlined `Risk::evaluate` and `Ledger::fill` into the benchmark loop at 85f70d8 and calls them now, after other code in the binary grew. In `pm_exec` both builds call `Risk::evaluate` out of line, and the submit stage is unchanged (p50 167 vs 169 ns); engine p50 546 vs 555 ns and 535k vs 509k messages/s, across the audit and later steps (resolutions, tick changes, stale legs, leg-risk check); not broken down further. Not forced inline: the production path does not inline it either.

## Bare metal (2026-10-12)

Conditions: HW.md H1-H12 (turbo off, CPU 4, no isolation yet). Counters per event come from `book_study` (stderr `counters,` lines, both hybrid PMUs).

- R11 Tick book, `book_study book:tick` (S120825-v50, 5 symbols, 44.6M events): 117.9 cycles, 248 instructions, 1.61 L1d misses, 0.017 LLC misses, 1.66 branch misses per event, so the book is bound by instructions and mispredicts, not memory. Removing an order now selects the head/tail address instead of branching on it, and clearing a window bit is branchless: 113.2 cycles and 1.45 branch misses with the first change, 111.9 and 1.39 with both; batch 2.03-2.05 s -> 1.93 s; p50 48.2 -> 47.4 ns, p99 159-163 -> 161-164 ns (overlapping runs). `book_replay` output is byte-identical before and after on all 12,077 symbols of S112825 and matches the map book.
- R12 Profile-guided build (`scripts/pgo.sh ~/data/store-S112825-v50 ~/data/ref/pm-snap`, measured on data it was not trained on): `pm_live --replay ~/data/pm-live/20261009T160027Z` parse p50 550 -> 500 ns, p99 3053-3065 -> 2979 ns, engine p50 175-178 -> 169-170 ns, same decision hash; tick book unchanged (1.93 s both). Adopted for `pm_live` runs (build/pgo-use); CI keeps the plain presets.
- R13 All five ITCH days through `book_replay ... tick` on one core: S112825 353M frames 31.8 s, S120825 650M 60.7 s, S120925 590M 54.6 s, S121025 847M 81.4 s, S121125 775M 72.6 s (about 11M frames/s); 0 check failures on 12,077-12,139 symbols per day. Stores are lz4 (ingest default). zstd for S112825: 4.58 GB vs 5.17 GB but 46.9 s vs 31.7 s replay, identical output; lz4 stays.
- R14 Prediction-market decoder after R12: IPC 2.83, `Decoder::string` 17% of cycles with the AVX2 quote scan already in place; R4 bounds what a simdjson-style rewrite could gain (about 15%). Not pursued.
- R15 Book worst case. Instrumenting the timed loop showed every event over 5 us (276 on S120825, 5 symbols) was a pool growth (mmap, pre-fault, copy: 115-300 us for 0.5-4 MB), plus two recentres at 44-48 us. `Pool` now grows by mremap into a 2 MB-aligned range, pre-faulting only the new part; a pool that outgrows 4 KB pages keeps its first 2 MB as a separate small-page VMA, because moving 4 KB pages under MADV_HUGEPAGE let khugepaged collapse them later and stall the owner 77-460 us. Recentre walks only the radix levels inside the new window (44-48 -> 30-36 us). `book_study book:tick` max 292-299 -> 36-43 us, p50 42.5 -> 41.0-41.7 ns, p99 unchanged; full-day `book_replay` S120825 59.9 -> 54.6 s; output byte-identical on S112825 and S120825 (uncore pinned, H18).
- R16 Live paper runs on bare metal (Wi-Fi, trading thread on isolated CPU 4, `native` build, per message, p50 / p99). 60 s, default events: sleeping threads kernel to ring 103-106 / 157-168 us, ring to decision 53-86 us, so wire to decision about 190 us (WSL2: about 280); `--spin --spin-feeds` kernel to ring 6.5-7.2 / 82-99 us, ring to decision 2.1-2.2 / 17-18 us, so about 9 us (WSL2: 39). `--feed-cpus 6,7` (new: pins feed threads) against unpinned over four alternating 60 s runs with 1,000 tokens on two connections: kernel to ring p50 5.3-10.3 vs 9.1-9.2 us, no difference measurable over Wi-Fi. Queue p99.9 is about 2 ms in every 60 s run and 0.37 ms over 180 s (27.6k events; wire to decision 2.1 / 10.9 us after the ring): a fixed burst at subscription, when every book snapshot arrives at once.
- R17 Full-day `book_replay` on a thread pool (`THREADS=16`, the 16 non-isolated CPUs: 4 P-cores with SMT and 8 E-cores). Scaling on S112825 before this change: 1 thread 29.3 s, 2 14.9 s, 4 7.7 s, 8 5.4 s, 16 4.5 s; at 16 threads 240k context switches, 5.9 s system time, profile showing TLB-shootdown IPIs and mmap-lock waits: every symbol built a fresh book and unmapped its pools at the end, 12k times a day. Each worker now keeps one book, cleared between symbols and dropped only after a symbol over 65,536 orders: 16 threads 4.5 -> 2.9 s (context switches 1.5k, system 1.3 s), 1 thread 29.2 -> 25.5 s. All five days at 16 threads, against main: S112825 4.6 -> 2.9 s, S120825 7.6 -> 5.6 s, S120925 7.7 -> 5.1 s, S121025 13.4 -> 7.0 s, S121125 9.9 -> 6.8 s, 114-121M messages/s, output byte-identical, 0 check failures.
- R18 Pre-faulting grown pools, revisited. At the first crossing into huge pages the new part does not start on a page, so `MADV_POPULATE_WRITE` failed and those pages faulted on use; making it succeed raised the book max to 225-238 us (several MB zeroed inline). The code now states the rule (pre-fault only from a page boundary) instead of relying on the error. Interleaved against never pre-faulting, with 18 GB of page cache from concurrent downloads: max 39-65 us (one 259 us) vs 44-77 us (one 326 us), within noise; R15's 36-43 us was measured with a cold page cache.
- R18 Full-day replay scheduling. On 16 threads, CPU time over wall time shows 12.6 of 16 threads busy (S061226). Handing symbols out largest first (message counts from the store index) raised that to 13.8 but did not shorten warm runs over all eight days (55.9 s against 56.5 s): the remaining gap is SMT siblings and E-cores, not a straggler. Not adopted. Replaying S061226 also failed `book_replay`'s persistent-cross check on SPCX (IPO): the book stayed crossed 680 ms after the IPO cross while its executions were reported, identically in the map and tick books. Crosses that start within 1 ms of a cross (Q) message are now exempt; all eight days pass, and only the `max_cross_ms` column and that symbol's check change.
